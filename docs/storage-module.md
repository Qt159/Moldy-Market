# Storage module

## Architecture

The Spring backend owns file metadata in PostgreSQL and object bytes in a private S3 bucket. The browser receives a short-lived presigned `PUT` URL. Object keys are generated by the backend as `<purpose>/<owner UUID>/<random UUID>.<extension>`; clients cannot choose the key. AWS credentials come from `DefaultCredentialsProvider` (use an EC2/ECS/EKS role in deployment).

The bucket remains private. Upload uses presigned `PUT` because that is the current API contract. The backend verifies the object at confirmation time; `PUT` does not impose a pre-upload content-length range, so an oversized object can consume S3 bandwidth/storage until confirmation or cleanup.

## Upload and confirm

1. `POST /api/v1/files/presigned-url` requires authentication. The controller reads the UUID from the existing `CustomUserDetails.getUserId()` principal. The backend validates the purpose, accepted MIME type, filename length, and declared size, writes a `PENDING` row, and signs a `PUT` request with the expected `Content-Type`.
2. The client uploads the bytes to S3 with that exact `Content-Type` header.
3. `POST /api/v1/files/{fileId}/confirm` is owner-only. The backend calls `HeadObject`, compares actual size and S3 content type with the stored request, then streams the object through signature and decoder validation. JPEG, PNG, and WebP must decode as an image and stay under the 16-megapixel decoder limit; PDFs must start with `%PDF-`. The backend does not buffer the full object in heap.
4. A verified object becomes `AVAILABLE`. A metadata/signature/decoder failure is stored as `REJECTED` and scheduled for S3 cleanup without throwing in the transaction that persists rejection. Missing object is a client error and leaves the upload `PENDING` so the client can upload and retry.

Image limits are 10 MiB; PDF limit is 20 MiB. Request metadata is not proof of content; confirmation validates the stored object. Presigned URLs expire in 5 minutes by default and may be configured up to the SigV4 seven-day limit. Keep them much shorter in production. The signed content type must match the upload header.

| Purpose | Accepted types |
|---|---|
| `PRODUCT_IMAGE`, `USER_AVATAR`, `DISPUTE_EVIDENCE` | JPEG, PNG, WebP |
| `APPRAISAL_EVIDENCE`, `APPRAISAL_REPORT` | JPEG, PNG, WebP, PDF |
| `ORDER_DOCUMENT` | PDF |

The [TwelveMonkeys WebP ImageIO plugin](https://github.com/haraldk/TwelveMonkeys) supplies WebP decoding. No PDF parser is used; validation checks the PDF signature and metadata, not the safety of active PDF content. Presigned PDF downloads use `Content-Disposition: attachment`; retain that behavior unless a separate sanitizer/scanner is introduced.

## Download authorization and linking

`GET /api/v1/files/{fileId}/download-url` currently authorizes only the file owner and only while status is `AVAILABLE`; other users receive a not-found response to avoid disclosing file IDs. This is deliberately restrictive.

The current business models do not store `StoredFile.id` references: products store HTTPS URL strings, appraisal reports store URL strings, disputes store an `images_url` string, and orders have no file association. `linkedAt` is never maintained by those modules. Consequently the backend cannot safely prove product visibility, order participation, appraisal participation, or dispute participation from a file ID. Do not add a permissive purpose-based download fallback. Before enabling buyer/seller/appraiser cross-user download or relying on linked-file deletion protection, migrate these business fields to file IDs and add transactional link/unlink calls that verify both resource membership and the matching `FilePurpose`. That integration is required for shared files in production.

## Delete and cleanup

Deleting a file first commits `DELETE_PENDING` in PostgreSQL; the row becomes inaccessible before S3 is called. The S3 delete is performed outside that DB transaction. On success, a second transaction changes status to `DELETED`. On S3 failure, the row remains pending and the scheduled job retries. A crash after S3 deletion but before the DB update is safe to retry because deleting a missing S3 key is idempotent. A PENDING upload's deletion waits until its presigned URL expires so an outstanding URL cannot recreate the object after cleanup.

The scheduled cleanup job queries bounded, indexed batches. It changes old unconfirmed uploads to `DELETE_PENDING`, deletes their objects (S3 deletion succeeds for absent objects as well), and retries failed deletions. Invalid uploads remain `REJECTED` while their object deletion is retried. Defaults: pending upload expiration 24 hours, scan every 1 hour, batch size 100. Retry attempts and timestamps are recorded; retry cadence follows the configured job interval rather than exponential backoff.

The job does not scan the entire table. S3 delete failures schedule exponential retry from 5 minutes up to 1 hour by default; cleanup still processes a bounded batch of other records. Indexes cover owner, status/creation time, old PENDING rows, deletion retries, and the unique object key. The `linkedAt` check is effective only after business modules begin recording links; legacy URL-based references are not discoverable safely (see blocker above).

## S3 deployment configuration

Sample environment values (no credentials):

```dotenv
AWS_S3_BUCKET=moldy-market-staging-files
AWS_REGION=ap-southeast-1
AWS_S3_UPLOAD_EXPIRATION_MINUTES=5
AWS_S3_DOWNLOAD_EXPIRATION_MINUTES=5
STORAGE_CLEANUP_INTERVAL=1h
STORAGE_PENDING_EXPIRATION=24h
STORAGE_CLEANUP_BATCH_SIZE=100
STORAGE_CLEANUP_RETRY_INITIAL_DELAY=5m
STORAGE_CLEANUP_RETRY_MAX_DELAY=1h
```

`S3Properties` validates the bucket, region, and expiration values during startup. Do not set `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` in deployment configuration; attach a workload IAM role. The role needs `s3:PutObject`, `s3:GetObject` (includes `HeadObject`), and `s3:DeleteObject` on only the application bucket's required object paths. It does not need `s3:ListBucket` for the implemented calls. If bucket default encryption uses a customer-managed KMS key, grant the role the required KMS encrypt/decrypt permissions for that key.

For each bucket/environment:

- Enable all S3 Block Public Access settings and Object Ownership `BucketOwnerEnforced`; do not use ACLs.
- Require TLS in the bucket policy (`aws:SecureTransport` must be true). The AWS SDK and presigned URLs use HTTPS.
- Enable bucket default server-side encryption (SSE-S3 or SSE-KMS). If using SSE-KMS, confirm the presigned PUT flow and IAM/KMS key policy in staging.
- Configure CORS only for the exact frontend origins. Allow `PUT` (and `GET`/`HEAD` only if the browser reads objects directly), allow `Content-Type` plus any required SSE headers, and expose only needed response headers such as `ETag`. Do not use `*` origins in production.
- Do not configure object expiration on the active purpose prefixes: lifecycle cannot distinguish an old unlinked upload from an actively referenced object. The DB cleanup job owns abandoned object cleanup. An `AbortIncompleteMultipartUpload` lifecycle rule is safe if multipart uploads are later enabled.
- Keep presigned URLs and their query strings out of application logs, analytics, and support tickets.

Example workload-role permissions (replace the bucket name; bind this policy to the compute role, not a user key):

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
    "Resource": "arn:aws:s3:::moldy-market-staging-files/*"
  }]
}
```

Example bucket policy statement to reject plaintext transport (merge it with the environment's existing policy):

```json
{
  "Sid": "DenyInsecureTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::moldy-market-staging-files",
    "arn:aws:s3:::moldy-market-staging-files/*"
  ],
  "Condition": {"Bool": {"aws:SecureTransport": "false"}}
}
```

Example CORS rule; replace the origin with the actual frontend origin and add `GET`/`HEAD` only if the frontend reads signed downloads with browser JavaScript:

```json
[{"AllowedOrigins":["https://app.example.com"],"AllowedMethods":["PUT"],"AllowedHeaders":["Content-Type"],"ExposeHeaders":["ETag"],"MaxAgeSeconds":300}]
```

The module does not configure bucket policy, public access block, CORS, encryption, lifecycle, or IAM through application code. Verify those AWS controls in infrastructure-as-code and staging; source code cannot prove the deployed bucket settings.

## Database migration

Flyway migration `V2__harden_stored_file_storage.sql` creates `stored_files` when absent, adds deletion retry fields to existing tables without dropping rows, removes duplicate single-column object-key unique constraints, and creates the storage indexes. Existing non-Flyway databases use the repository's baseline version 0 configuration; review the Flyway history and schema before deployment. Run the migration against a restored staging copy before production. Hibernate `ddl-auto=update` is still enabled for the application's pre-existing domain schema; this storage migration does not constitute a complete schema migration for every module.

## Local test and staging rollout

Run focused storage tests:

```powershell
mvn -Dtest=FileControllerTest,FileContentValidatorTest,S3FileStorageServiceTest,S3PropertiesTest,FileAuthorizationServiceTest,StoredFileStateServiceTest,S3FileCleanupJobTest,StoredFileMigrationPostgresTest test
```

Unit tests mock S3 and do not send objects to AWS. The migration test uses PostgreSQL Testcontainers and is skipped when Docker is unavailable. For staging: apply Flyway, supply the bucket/region and workload role, verify bucket controls above, upload valid and spoofed image/PDF fixtures, confirm an abandoned upload is cleaned after the configured interval, and inspect logs for cleanup retry counts. Monitor PENDING age, REJECTED files, DELETE_PENDING age/attempts, and S3 4xx/5xx errors.

## Known production blockers

1. Shared business-resource access is not implemented until Product, Appraisal, Dispute, and Order persist file IDs and expose reliable membership/visibility checks. The current storage API is owner-only.
2. `linkedAt` is not set by business modules, so current legacy URL references cannot be protected from owner deletion by this field. Migrate links before relying on this guard.
3. PDF validation verifies the signature, not full document structure or active content. Add malware scanning/sanitization if PDFs are rendered or redistributed.
4. Upload size is checked after S3 upload because the API retains presigned PUT. Staging must confirm frontend behavior; presigned POST with a content-length range would require an API/client protocol change.
5. Bucket access, encryption, TLS policy, CORS, IAM, and lifecycle are deployment controls and were not verifiable from this repository.
6. Storage state and retry tests currently use unit mocks. Run PostgreSQL migration/transaction tests and S3-compatible integration tests in an environment with PostgreSQL and LocalStack/AWS before calling the module production-ready.
